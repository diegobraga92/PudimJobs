Significant engineering decisions, one row each: what we chose, what we chose it
over, and why. Dates and full context live in git history.

| 016 | Tailored CVs as self-contained `generated_cvs` artifacts | non-current `master_cv` versions | Master CV history stays clean, each artifact carries its own content, and `rule`/`llm` variants are scored by the same scorer |

| 018 | `manual` source type (watchlist) + in-app re-check reminders | pretending to scrape login-walled boards, cookie auth, dropping those boards entirely | The engine cannot reach authenticated/anti-bot boards by design (see `scraping.md`); a hand-checked source keeps them tracked with cadence in `config` (no migration) and the sweep only reminds — it never fetches. The cadence contract is published once (`GET /api/sources/manual-metadata`) and validated (1–365 → 422); clients must **merge** `config` on update so engine-managed `next_check_at`/`reminded_at` survive |
| 019 | One shared `AppModalComponent` (fixed-overlay dialog) for transient forms | per-page inline expanding panels; a routed create/edit page per form | Create/edit forms used to render inline above the list (`showForm` + `<form class="panel form">`), pushing content down on Sources, Jobs, Alerts and Prep tasks. The modal reuses the global `.modal-backdrop`/`.modal` styles and the confirm-dialog conventions (backdrop click, Escape, `role="dialog"`), keeps the list in context, and collapses four copies of the pattern into one primitive. Full-page editors (CV editor, application detail) stay routed because they are destinations, not transient edits |
| 020 | Skills-section parsing splits on real separators only, and strips group labels | splitting on single whitespace and `/`; treating the CV's own `Group:` labels as a second grouping source | A label prefix (`Frameworks:`, `Cloud & DevOps:`) and multi-word names (`Apache Thrift`, `Test-Driven Development`, `CI/CD`) are both natural content for this section, so whitespace was never a delimiter: it shredded the names *and* the labels into fragments (`Frameworks`, `Apache`, `CI`, `CD`) that no taxonomy lookup could place, which is what piled into `Additional`. Splitting on commas/semicolons/pipes/bullets/2+ spaces — never a single space or `/` — plus stripping a known label prefix fixes it at the source, keeps the taxonomy the single source of grouping, and restores multi-word entries to `match_skills`. A label left alone on its line inside the block stays in the section instead of being read as the spoken-languages heading. Taxonomy entries shorter than the 3-char matching floor (`qt`) group but never match a JD. The label list is a fast path only, and a label glued to its values is fixed at the resolution step rather than by growing the list — see 022 |

| 021 | CV header renders as one flowing contact line at 8pt | keeping the "details" line + "links" line split; a smaller name; a narrower font family for the header alone; tighter page margins | The two-line header existed only because each field was unbreakable and adjacent fields offered no break, so one line could only overflow the page edge or be pre-split. Making the separator itself the break opportunity removes that trade-off: the block packs greedily onto one line and wraps *between* fields when it has to, never mid-token and never past the margin. 8pt is the measured size at which a real five-field header (email, phone, location, two links — 109 characters) fits DejaVu Sans inside the 17.4cm A4 text block: 472.9pt of the 493.2pt available, where the previous 9.5pt wrapped onto a second line (the ATS template, at its wider 11pt, needed ~639pt of 487.6pt). DejaVu's large x-height keeps 8pt legible, and it needs no font the render host may lack. Both templates, the DOCX (now on the same A4/1.8cm page box, since Letter's 432pt is too narrow) and the editor preview follow the same rule; resetting the UA's 8px `body` margin, which had silently narrowed the content box to 16.98cm, is part of the same fix |

| 022 | Skill labels are recognised by *shape*, and every entry resolves to its canonical skill(s) | extending the closed label word list; splitting entries on `/`; one skill per entry | The word list from 020 only knows the labels we anticipated, so a CV writing `Frameworks & Tools:`, `Databases & Analytics:` or `Systems & Tools:` kept its label glued to the first value on the line (`Frameworks & Tools: Qt`), which no taxonomy lookup can resolve; the label words that never got glued (`Additional`, `Methodologies`) then became skills, and the whole tail of the section rendered as one `Additional` line. A label is now recognised by shape — at most four words, no digits, and no word the taxonomy knows as a skill (that last rule is what keeps `AWS: EC2` and `CKA: Certified Kubernetes Administrator` intact) — with the word list kept as the fast path; *every* label on a line is stripped, because PDF extraction merges two labelled columns onto one line, and brackets are unwrapped only when balanced, so `Test-Driven Development (TDD)` keeps the acronym an ATS searches for. Entries then resolve through a ladder: exact/alias → all parts of a `/`-or-`&`-compound (`JavaScript/TypeScript`, `Protobuf/gRPC`) → the longest known name inside the entry (`Google BigQuery`, `Test-Driven Development (TDD)`), the entry itself when nothing matches. That puts compounds in their real groups instead of `Additional`, and lets `match_skills` credit a CV that spells the JD's skill as half of a compound. Two rules keep it honest: a compound whose parts disagree (`AWS/PostgreSQL`) still falls to `Additional` rather than being placed on a coin flip, and the CV's own spelling is never rewritten — the tailorer reorders its own entries instead of injecting a second copy of a matched skill |
| 023 | Bulk job cleanup by `created_at` age and/or source, preview-first, applications protected by default | deleting per job in the UI; filtering by `posted_date`; deleting every match without a preview; excluding tracked jobs server-side with no opt-in | The list is where the clutter shows up (a boarded source can add hundreds of rows), and the DB makes the stakes asymmetric: `applications.job_id` is `ON DELETE CASCADE`, so a careless cleanup silently destroys the pipeline history, while `generated_cvs.job_id` merely `SET NULL`. Age is matched on `created_at`, never the nullable `posted_date` that scraped rows often lack — an age filter there would silently spare whole sources. `POST /api/jobs/cleanup` therefore defaults to `dry_run`, returns `{matched, deleted, protected}` so the dialog can show exactly what will go before anything is removed, requires at least one criterion (an empty body would mean "delete everything"), and is audit-logged (`bulk_deleted`). Opting into `include_with_applications` is the one way a tracked job is deleted, because that is the one way an application disappears |
| 024 | PT-BR CV export translated on demand by the LLM, with section headings from a fixed catalog | storing a translated `pt-BR` artifact per CV; a second `language` column/migration; asking the LLM for the whole document including headings | Nothing is persisted: like DOCX (017), the translated copy is rendered at download time from the same `structured_json`, so no migration is needed and the copy can never go stale after an edit. Headings are *chrome*, not content — the same words on every CV in a language — so they come from `cv_labels` (deterministic, and the reason a translated CV never mixes "Experiência" with "Summary"); only free text goes through `cv_translator`, whose prompt splits prose from data — job titles, degrees and every `skill_groups` label are translated, while skill entries, employers, institutions, names, dates, numbers and links never move — and whose reply is re-validated through `CVStructure` and rejected when it empties a section the input had filled. A CV that stores no `skill_groups` is grouped by the taxonomy *before* the call, because those labels (`Tools`, `Languages`) are English literals the renderer would otherwise print under a `Competências` heading with the model never seeing them; the reply is validated against that enriched structure, so flattening the section back to the flat list fails too. Two consequences are accepted: group-label wording becomes model-authored (it may differ between two exports of the same CV), and a reply that omits a group section is a 502 rather than a fallback to English labels. English is the stored language and stays LLM-free; a non-default language with the LLM off is a 409 (never a silent English download) and a failed translation is a 502. The client cannot read admin settings, so `GET /api/cv/capabilities` publishes `{llm_enabled, export_languages}` and the UI greys PT-BR out before the user picks it |
| 025 | "Add job" can import one posting from a URL: server-side fetch + parse into an **editable draft** that the user confirms through the normal `POST /api/jobs` | a browser-side fetch (CORS/anti-bot would break it and the SSRF guard would be bypassed); a new `scrape_source` run (a whole board for one page); a worker task; a new source per link; saving straight from the fetch without review | The pieces already exist and are hardened — `scrapers/utils.fetch_html` (SSRF guard, redirect cap, 2 MB cap, UA rotation), the same JSON-LD→CSS parsers the engine uses, `llm_client`/`llm_config` with graceful degradation — so the import is one synchronous call (`POST /api/jobs/import-preview`, `job_import_timeout_seconds`, `rate_limit_import`, like the source preview) and needs **no dependency, migration, event-schema change or worker task**. Extraction order is the project's (006): JSON-LD, then CSS, then an *optional* LLM gap-fill that only fills blanks and never overwrites a value the page provided; tags come from the page chips, else from the skill taxonomy (no spaCy in the API process). The draft is never persisted (004: no raw HTML, only plain-text description) and the dialog patches only non-empty fields, so a user's own typing survives. A duplicate URL is a warning with `existing_job_id`, not a block — the user may legitimately track the same posting twice. Fetch/parse failures answer **200 with `error`** (the source-preview contract) so the dialog can explain the reason without losing the form. `robots.txt` is skipped by default for this one-off, user-initiated fetch (the ad-hoc rule the source preview follows; `job_import_respect_robots` re-enables it). Known limit: JS-rendered boards (LinkedIn, Indeed, SPAs) return a shell, so the draft arrives empty with a warning and the user falls back to typing — the paid discovery providers remain the route to those boards |
| 026 | Any job is editable by hand in the UI (an edit dialog on the job page of both clients — web and mobile — over `PUT /api/jobs/{id}`), **description included** | a per-job "fetch this posting again" button (025 already does that, and a page that stored no description usually fails twice); `scripts/repair_sources.py` (it repairs extraction for a whole source, not one row); editing only the description | Tailoring is only as good as the text it receives: when a board renders its posting client-side or blocks the fetch, `description` lands empty, `parse_jd` extracts no skills, matching has nothing to score and `post_tailor` tailors a CV to nothing. The write path already existed for `hidden`; the gap was the UI. New description text invalidates `parsed_jd`, which is dropped so the next parse/tailor run re-reads it (the tailor task parses on demand), and every edit is audit-logged by field (`description` by size, never its text) so a hand-edited row stays distinguishable from what a scraper stored. Required labels are trimmed and blank ones refused with 422 — the feed groups and ranks on them |
| 027 | CV tailoring preserves the **whole employment history**: relevance decides *how much of a role* survives, never *whether the role exists* (**amended by 029**: the per-role space is uniform and the LLM's allocation is the model's call) | budgeting the page by keeping "the 3-4 best roles" (the LLM prompt); `drop_irrelevant` dropping every non-matching block (the rule engine); a reject-and-retry loop when the model omits a role; letting the model author the timeline | A role the tailor leaves out becomes an unexplained employment gap, and the dates of a job whose stack looks foreign are exactly the evidence a reader needs to place that gap: the rule engine's `drop_irrelevant` (default `True`) and the prompt's "keep 3-4 roles" were two spellings of the same bug. The history is now a contract. `tailor_cv` keeps every `experience` block in the master CV's order and spends relevance on bullets — a uniform `_BULLETS_PER_ROLE = 4` since ADR 029 (it was 6 for a role that shared a keyword and 2 for one that shared none) — which replaces `_FALLBACK_TOP_N`, and `used_fallback` now means *nothing matched at all* instead of "the top 3 were kept silently". Projects keep the old select-or-top-N behaviour: a project is not a timeline, so dropping one leaves no gap. The LLM prompt asks the model to fill two pages, keeps employer/title/dates/order and forbids omitting a role or reducing one to a bare header; the per-role bullet arithmetic it used to carry was removed in ADR 029, which left the allocation to the model. Because a prompt is a request and not a guarantee, `generate_tailored_cv_with_llm` enforces the rule *after* `CVStructure` validates: `_restore_missing_roles` re-inserts each role the model dropped *or returned with no bullets*, in its original position, with its own dates and its own first two bullets verbatim — nothing invented — and logs `llm_cv_roles_restored restored=N unmatched=M emptied=K`, where `unmatched` counts reply roles that trace back to no master role and are *kept* and reported (deleting an unrecognisable entry would be a second silent edit) and `emptied` counts bare-header roles that were replaced from the master CV. Role identity is checked in three tiers — the period the two roles share (dates folded, so `2022-07` and `Jul 2022` agree), then employer plus title, then the *set* of employer and title words, which is what also recognises a model's semantic fix to a stored CV whose two fields were swapped — so a reworded `Sr. Java Developer` is the same job, a promotion inside one employer stays two roles (two roles whose periods differ are never one job), and `_dedupe_roles` drops any second copy the reply still contains. The prompt-side trimmer no longer keyword-filters the reference (ADR 029): it gives up the optional sections and the project prose, then abbreviates the longest bullets in place, and never drops a role — so shrinking an oversized reference can never delete the employer the prompt is about to require. Accepted cost: a foreign-stack role still costs a date range and two lines, so a long history can legitimately need the second page; the worker's `cv_artifact_pages` / `llm_rewrite_page_retry` / `llm_rewrite_over_page_budget` handling remains the safety net instead of an automatic post-trim, which would delete precisely the roles this rule protects |
| 028 | A role header is split by **meaning, not position**: `title` is the half that names a job and `company` the employer, for *both* orders — and `scripts/repair_cv_fields.py` repairs CVs already stored the other way round | reading `"A — B"` as title-then-company (the old default); requiring one fixed separator order in the uploaded CV; an LLM call to fix the field order; leaving stored CVs alone and only fixing new imports | Plenty of CVs put the employer first (`"Axcient — Senior Software Engineer (Remote)"`, `"Embraer S.A. — Product Development Engineer (São Paulo, Brazil)"`, `"Independent Contractor — Senior Software Engineer"`), and splitting by position stored every role of those files with its two name fields inverted. The preview hides it — "Acme / Jul 2022 — Oct 2025 / Senior Software Engineer" reads perfectly naturally — while the exports, the rule variant and tailoring's role matching all carry the swap: the model reads the master CV semantically, writes the fields correctly, then no reply role matched its master counterpart, so the guard re-inserted the whole history next to the model's copy and the tailored CV listed every role twice. `cv_parser` now scores both halves against a folded vocabulary of job words (`role_title_score`, EN + PT) and swaps only when the *last* half scores strictly higher, so the traditional title-first reading is unchanged for every ambiguous header (neither side names a job, or both do — including a company that merely contains a job word, like "Engineer Solutions Ltd"). `scripts/repair_cv_fields.py` migrates what is already stored, dry-run first and `--apply` to write: a role is repaired only on the unambiguous signature — the stored title names no job while the stored employer *ends* in one (a head-word test, so `"Sales"` / `"Engineer Solutions Ltda"` is left alone) — only the two names move, every other field is untouched, and the tailored artifacts derived from a repaired CV are dropped (opt out with `--keep-artifacts`) because the tailor task reuses an artifact for the same CV/job pair and would keep serving the swap. The parser is the fix; the script is the migration for data parsed before it |


| 029 | **AI-first tailoring**: the `llm` variant is the artifact a run offers, links and opens by default; its prompt is a *brief* and the rule engine is a uniform fallback | keeping the rule engine as the default artifact with the LLM as an optional "polish" layer; keyword-ranked bullets (6 per matching role, 2 per other); a recipe-style prompt that fixed the bullet counts per role; pre-trimming the model's input to the keyword-relevant 6k chars | The LLM is the only part of a tailor run that can judge which experience wins *this* job, so the pipeline was organised the wrong way round: the artifact the user actually sent was the one produced by a keyword count. Three symptoms followed from that. (1) *The balance was a formula.* "Give the 2-3 best roles up to 3-8 bullets each and every other role at least 2" told the model that sharing a keyword with the JD *is* relevance, so it padded roles it had nothing to say about and compressed the ones where the story was, while the fallback's 6-vs-2 split delivered the same judgement with none of the reading. (2) *The input was pre-decided.* `_fit_cv_for_prompt` trimmed the master CV to keyword-selected bullets before the model saw it — the model could not keep a bullet it never received, and the bullets a keyword score drops are exactly the ones a human writer would keep. (3) *The default was arbitrary.* Both variants of a run share `created_at`, so "newest first" left the panel opening on whichever row Postgres returned, and the worker only ever linked the rule artifact. Now: the prompt states the goal and the invariants only (source of truth, complete history in order, no role as a bare header, ≤2 pages) and lets the model spend the space; the bare-header floor and the historical facts are enforced in code (`_restore_missing_roles` restores/drops, `_unverified_numbers` reports), never asked for twice. The input is *abbreviated, never filtered* (optional sections, then project prose, then the longest bullets half-length; the budget is 32k chars so this is the exceptional path), because every role and bullet must reach the decision-maker. The API orders `created_at desc, llm first`, the worker links/prefers the `llm` artifact when one exists and never overwrites a recorded *Use this one*, and both panels open on linked → `llm` → first. The fallback keeps its job — a CV when the LLM is off or fails — but it no longer pretends to rank: `_BULLETS_PER_ROLE = 4` for every role, in the CV's own order, with the match still reported (`matched_skills`, `relevance`) instead of buying space. The page budget is checked after the render it is about: one corrective retry with the real page count (`llm_rewrite_page_retry`), then a warning (`llm_rewrite_over_page_budget`) — never an automatic trim, which would delete the roles ADR 027 protects |

## Notes

- **Datastores** — PostgreSQL is the only database; Redis is the Celery result
  backend, rate-limit store and circuit-breaker store; RabbitMQ is the event
  broker. Every choice above is reversible behind `DATABASE_URL`/`REDIS_URL`/
  `CELERY_BROKER_URL`.
- **Role identity (027/028)** — a tailored role is matched to its master
  counterpart on what a rewrite cannot change: the period first, then employer +
  title, never on the exact string. That is what makes a reworded title or a
  reformatted `Jul 2022` one job instead of two — and the reason a stored CV with
  its `title`/`company` fields inverted used to double the whole history, which
  `scripts/repair_cv_fields.py` fixes in place (dry-run first).
- **Tailoring (006/013/016/029)** — the AI rewrite is the CV a run offers: the
  worker links and prefers the `llm` artifact when one was produced, the API
  lists it first within a run, and both panels open on it (linked → `llm` →
  first). The deterministic engine is the *fallback* — it always runs and always
  produces an artifact, so a disabled or failing LLM still yields a CV — but it
  condenses every role the same way instead of ranking them. Both variants are
  scored by the same deterministic ATS scorer so they can be compared. An
  explicit *Use this one* is never overwritten by a later run. No tailor run
  ever creates a `master_cv` version.
- **Full history (027)** — tailoring never filters `experience`, in either
  variant: the fallback keeps every role with its first four bullets (no
  keyword ranking — a score that decides *space* was the rule engine pretending
  to judge), so no run can invent an employment gap. The `llm` variant's brief
  is enforced in code rather than trusted — a role the model drops *or returns
  as a bare header* is re-inserted with its own dates and its own verbatim
  bullets, and a role it writes twice is de-duplicated
  (`llm_cv_roles_duplicated`) because one job can never appear twice. Numbers
  the reply uses and the master CV does not contain are reported
  (`llm_cv_unverified_numbers`) and never rewritten: reformatting a metric is
  not inventing one. Only projects may be dropped or shortened, because a
  project is not a timeline.
- **Cleanup (023) & PT-BR export (024)** — bulk cleanup is *always* preview-first
  (`dry_run` defaults to `true`) and never removes a job that has an application
  unless the caller opts in, because the cascade would take the application with
  it. Translated exports are computed per request and never stored: the English
  PDF stays the one canonical artifact, the translated copy is rendered from the
  same structure, and a non-default language is refused with 409 rather than
  silently served in English. The translator is handed the taxonomy's skill
  grouping when the CV stores none, so the group labels (`Tools`) translate with
  the rest of the copy instead of rendering in English under a translated heading.
- **URL import (025)** — the import endpoint is a *preview*: it fetches and parses
  one page, persists nothing and answers 200 even when the page could not be read
  (`error` explains why), exactly like the source preview. Saving is the existing
  `POST /api/jobs`, so there is one write path and one place that validates a job.
  The LLM only fills blanks the page did not provide, `warnings` are English
  diagnostics (as in the source preview) rather than translated copy, and a URL
  that is already saved is reported through `existing_job_id` instead of being
  refused.
- **Manual job edits (026)** — the job page's edit dialog (both clients) is the escape hatch for a
  source that stores a posting without its description: parsing, matching and CV
  tailoring all read that text, so filling it in by hand turns an unusable row into a
  normal one. Saving new text drops `parsed_jd` (the requirements derived from the old
  text) and the page re-queues parsing; edits are audit-logged by field, with the
  description recorded by length so the log does not grow with the posting.
- **Connection pooling** — sessions use `NullPool` (a fresh connection per
  session). Correct for short-lived worker tasks; switch to
  `AsyncAdaptedQueuePool` (`pool_size=10`, `max_overflow=20`) above ~1k req/s.
- **ATS scoring weights** — skills 40%, keywords 15%, completeness 20%,
  readability 25%; an LLM review is blended in at 30% when configured and never
  blocks the deterministic score.

## Event schema (ADR 003)

`job.new` events are JSON on the durable topic exchange `pudimjobs.events`, with
version-scoped routing keys (`job.new.v1`, `job.new.v2`, …) and a `version`
integer in every payload. Schemas live in `api/events/` so the API and workers
share them.

**Compatibility contract**

1. Additive only — a new field MUST be optional with a sensible default
   (`None`, `False`, `[]`); older consumers must still deserialize it.
2. Deprecation window — a deprecated field keeps its default for two schema
   versions before removal.
3. Version bump — any non-additive change is a new `version`, never an in-place
   edit. Consumers bind with `job.new.#` and check `version` before parsing.

**Versions**

| Version | Fields |
|---------|--------|
| v1 | `version`, `event_id`, `job_id`, `source_id`, `title`, `company`, `url`, `posted_date`, `tags`, `timestamp` |
| v2 (planned) | adds `salary_range: str \| None = None`, `remote: bool \| None = None` |
